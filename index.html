OCR教学示意与本次测试条件

OCR里，4096是什么意思？

OCR的上下文可以包含图片编码后的信息、输入指令和已生成的识别内容；具体位置数量由图片编码、分词及模型处理方式决定。

本次实测输入：同时处理256个请求；每个请求的注意力读取4096个有效缓存位置。

每个请求只有一个当前查询位置。查询向量与这4096个位置的键值缓存均由脚本构造，用来比较两个算子的速度。本次没有真实文档图片或模型权重，4096也不是一张图上的字数。

表格中的完整名称统一为“每个请求的注意力上下文长度（缓存位置数）”；长短混合输入显示最大值，各请求实际有效长度可以不同。

深入理解

PA / FIA 从哪里来，为什么这一步能换？

这次换的是“读取同一份分页缓存、计算同一个解码注意力”的实现。两边都做相关性计算、softmax 归一化和加权汇总。能在我们限定的解码路径切换，是因为输入、可见缓存位置和输出语义对齐；换个函数名还不够。

为什么数学上可以对齐：一个请求只查询一个当前位置

设模型正在生成一页 OCR 结果。这个请求当前只有一个查询位置，它要参考缓存中所有允许看到的键和值。先用查询与各个键算相关性，再把分数归一化为总和为1的权重，最后对值向量加权求和。分页只改变这些键和值在哪里，不改变这道计算题。

对每个查询头：
关注分数 = 查询向量 × 有效键向量的转置 ÷ √128
输出 = softmax（关注分数 + 遮挡规则）× 有效值向量
本实验无额外位置偏置、无滑动窗口、无 KV 量化；12个查询头共享2个键值头，每6个查询头对应一个键值头。

GQA（Grouped Query Attention，分组查询注意力）表示多个查询头共享一组键和值。比如这里查询头0至5使用键值头0，查询头6至11使用键值头1。PA 和 FIA 都收到“12个查询头、2个键值头”，所以不需要把缓存复制成12个头。独立 CPU 标杆则显式按这个分组关系计算，核对两边输出。

同一块表怎么读：299个有效位置的教学例子

以下数字是教学示意，非新增实测点。每块128个位置，请求有299个有效缓存位置；其块表为 [5, 2, 7]，不是按物理地址连续排列。

物理块5逻辑位置0–127
读取128个有效位置
物理块2逻辑位置128–255
再读取128个有效位置
物理块7逻辑位置256–298
只读取前43个位置
其余85个位置不参与计算

PA 读取 context_lens=299；FIA 读取对应的 actual_seq_lengths_kv=299，两边拿同一张块表。它们必须只看299个有效位置，不能因为最后一块还有空位，就把未使用位置也纳入 softmax。不需要先把这些块拼成一条连续缓存。缓存中是否包含本次处理位置，取决于调用前写入与长度更新；双方必须使用同一时刻的缓存和相同有效长度。

对单查询的标准自回归解码，当前位置可以看到自己和之前的有效位置，缓存中没有应被看到的“未来”。FIA 的相应因果掩码与 PA 的有效长度截断可以在这个子场景对齐。但滑动窗口、任意遮挡、一个请求一次处理多个查询位置时，仅凭有效长度就不够。PA 这个简单入口不接收通用掩码，不能把 FIA 的掩码参数直接丢掉。示意解释不证明 FIA 内部完全不执行掩码处理；实测仍传入脚本中的掩码和 sparse_mode。

框架实际改了什么：扩大图配置适用范围，继续保留解码边界

修改前

图配置为 FULL_AND_PIECEWISE 时，原选择函数的图模式条件不满足；即使当前这一批请求全部进入标准解码，正常头维场景仍回退到 FIA。

FULL_AND_PIECEWISE（混合图模式）决定服务如何组合完整图与分段执行；当前算子仍可能处在纯解码步骤。服务的总图配置与本步骤的请求阶段是两个判断。

选择函数同时接受 FULL_DECODE_ONLY 和 FULL_AND_PIECEWISE，命中已配置的 PA 形状时沿用现有 PA 实现。

证据已支持

两边使用相同输入和页表；设备执行的是不同 kernel。绕开 Python 逐次提交影响后，大批次的设备耗时差仍在，因此不能把全部收益归于 Python 层、缓存复制或图模式更名。

FIA 自身也是融合实现，本轮并没有“FIA 分成许多 kernel、PA 只发一个”的差别。两边都能分页，不能归因于“只有 PA 省了连续缓存拼接”。

合理推断，尚非根因实锤

不同内核的任务切分、每核工作量、读取共享键值头的方式、缓存复用和归约策略，可能对请求数及上下文长度有不同取舍；小批次反而 FIA 更快，支持存在形状相关的选择差异。

要确认哪一种取舍造成收益，仍需与实际二进制匹配的内核源码、切分参数及访存/流水数据。不能仅凭名字里的“专用”“融合”判定原因，也不能凭单个流水活动比例当带宽利用率。

推荐使用场景：什么时候选PA，什么时候选FIA？

PA是分页注意力，FIA是融合推理注意力。对我们这次已测的解码形状，先看设备这一步同时处理多少请求，再看每个请求读取多少个缓存位置。客户端总并发256，不代表每个解码步骤一定组成256个请求。

优先考虑 PA

请求积累后，组成较大解码批次

适合以吞吐为目标、每步能同时处理32、64、128或256个请求的已测组合；每请求上下文长度分别为128、512、2048、4096或8192个缓存位置，20个组合均稳定PA更快。

实测例子：每步256个请求，每请求4096个缓存位置，PA注意力算子耗时少32.45%。

优先考虑 FIA

请求较少，且上下文匹配FIA优势形状

01 / 理解对象

同一段解码，换两种注意力实现

想象 OCR 模型正在读一张文档图片，并逐字生成识别结果。在解码（decode）阶段，注意力读取已缓存的上下文信息，为预测下一个模型处理单元提供结果。这次 demo 只截取其中一次注意力计算，不运行读图、完整模型层或服务调度。

03 / 收益证据

真实设备 kernel 也更快，收益不全是 Python 开销

正式测速使用 NPU event（设备事件）测两次时间标记之间的间隔，它还可能包含设备流空隙。为了确认算子本身的差别，我们另外开启 profiler（性能采集器），读取设备 kernel（在 NPU 上执行的计算任务）的记录。

正式测速怎样做

先固定输入，完成预热同一 Q/K/V、块表与有效长度；预热 20 次。输入生成、分配和 workspace 查询不计时。
两种执行模式分开比较eager 每轮调用 100 次；graph 每轮回放 100 次，一次图含同算子 16 次，最后除以调用数。
原测六轮换顺序；本页统一去首轮PA→FIA 与 FIA→PA 交替；本页报告后五轮中位数，余下五个配对都满足 1.05 倍优势才判稳定赢家。
计时之后验输出计时前把输出写成 NaN（非数），计时后验证结果，避免“没有实际执行”却拿到漂亮时间。正式测速不开 profiler。

另外采 kernel，独立核对

CPU+NPU、Level1、PipeUtilization；每步分别处理8、64、256个请求，每个请求固定读取4096个缓存位置。每种算子采 20 次 replay × 16 个调用。

Token · 模型处理单位

模型处理信息的基本单元。文字会按分词规则拆成单元，图片也会被编码成模型可处理的信息位置；两者都可能参与注意力。token数量不固定等于汉字数。独立测试中，每个请求的当前查询长度固定为1。

本解码步骤同时处理的请求数

一次设备计算同时处理的请求数。例如本步同时处理8个请求，与压测客户端的总并发不是固定一一对应。

每个请求的注意力上下文长度

当前注意力调用可以读取的有效键值缓存位置数量。它对应已处理的上下文，可能包括图片编码信息、输入指令和已处理的生成内容。相同长度输入中，各请求相同；长短混合输入中，表格给出最大值。实际计数以本步有效缓存长度为准；可能包含当前处理位置，不应一律理解为仅有“过去生成的文字”。

查询向量 / 键向量 / 值向量

查询向量与键向量计算相关性，用相关性权重对值向量加权汇总，得到本层输出。上下文键值缓存保存已经计算的键向量和值向量，下一步重复利用。

GQA · Grouped Query Attention / 分组查询注意力

多个 Query 头共享较少的 KV 头。本轮 12个查询头共享2个键值头，每组6个查询头共享一组历史。

每个注意力头的向量维数

每个注意力头的向量长度。本轮每头向量包含128个数值；12个查询头的总宽度为 1536，2个键值头的总宽度为 256。

Block / Block Table · 缓存块 / 块表

缓存块是固定大小的存储单元；块表是索引。例如第一个逻辑块可以存放在物理块 5，不要求物理连续。

View · 张量视图

用不同形状解释同一片内存。这里 [块数,128,2,128] 与 [块数,128,256] 的数值与字节不变。

ATB · Ascend Transformer Boost

昇腾 Transformer 算子库，本轮 PA 的实现来源。PA 这个算法名字不等于所有平台的某一个固定 kernel。

TND · Token / Head Number / Dimension

FIA 的一种输入排列：token 数、头数、头维。本轮每个请求只有一个当前 token，因此查询张量的当前 token 总数等于本步同时处理的请求数。

脑浮点16位格式（BF16） / FP64 · 浮点数格式

BF16 是本轮设备输入和输出格式；FP64 是 CPU 独立标杆的双精度格式。不是引入模型量化。

Profiler / Trace / Kernel · 采集器 / 记录 / 设备任务

profiler 记录运行事件；trace 是可分析的事件时间线；kernel 是设备实际执行任务。事件计时间隔与纯 kernel 时间不同。

微秒 · 时间单位

1 秒=1,000,000 微秒。893.52 微秒 约为 0.894 毫秒；这里只是一次注意力调用，不是整个 OCR 请求。

FIA/PA · 耗时比

比值 1.48 表示 FIA 用时是 PA 的 1.48 倍。PA 耗时减少率=1−1/1.48≈32.4%，不是减少 48%。

Oracle / Tolerance · 标杆 / 容差

oracle 是独立参考计算；容差是允许的数值误差。通过容差仅说明本次规则下符合预期，不证明逐位相同。

相对均方根误差 / 满足逐元素容差的比例

相对均方根误差 衡量整体误差大小；满足逐元素容差的比例 表示多少输出元素满足逐元素容差。二者不能直接换算成 OCR 准确率。

Prefill / Decode · 预填充 / 解码

prefill 处理输入上下文并建立 KV；decode 继续生成下一 token。本 demo 只测每请求单 Query token 的解码注意力。

Workspace / Tiling · 工作区 / 任务切分

workspace 是算子运行的临时空间；tiling 决定芯片上怎么分任务。本轮排除空间查询计时，未取得内部切分因果证据。
